# Умный кредитный кабинет предпринимателя

Прототип цифрового кредитного конвейера для малого и микробизнеса (хакатон Альфа-Банка, кейс «Умный кредитный кабинет предпринимателя»). Клиент выбирает кредитный продукт, подаёт заявку и получает результат в личном кабинете, а банковская часть проверяет данные, считает оценку риска и принимает решение. Состояние заявки сохраняется и меняется последовательно.

> Этот README пока командный: он объясняет, что где лежит и куда добавлять свои файлы. К сдаче разделы внизу («Запуск», «Сценарий проверки» и другие) заполняются полностью, потому что по ним эксперты будут проверять проект.

### Корень

| Файл | Для чего | Кто ведёт |
|---|---|---|
| `README.md` | Описание проекта и инструкция запуска (этот файл) | Вика, остальные добавляют свои разделы |
| `THIRD_PARTY_NOTICES.md` | Список сторонних библиотек, образов, моделей и смоделированных интеграций. Требование организаторов | Вика; каждый разработчик записывает сюда основные библиотеки, которые добавляет |
| `docker-compose.yml` | Единый запуск всех сервисов одной командой | Вика |
| `.env.example` | Список переменных окружения с **фейковыми** значениями. Настоящий `.env` создаётся локально и не коммитится | Вика; кто добавил новую переменную, дописывает её сюда |
| `.gitignore` | Что Git не отслеживает (секреты, `node_modules`, `target`, `.venv`, веса моделей) | Вика |
| `.gitattributes` | Единые переводы строк для Windows и Mac | Не менять |

| Папка | Что внутри | Что добавлять | Ответственный |
|---|---|---|---|
| `frontend/` | Веб-клиент: кабинет клиента и минимальный интерфейс сотрудника банка (React + TypeScript + Vite) | Исходники, `Dockerfile`, `package.json` и `package-lock.json` | Лиза |

| `mocks/` | Имитации внешних сервисов: ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес», БКИ, выписка | Исходники, `Dockerfile`, заготовленные ответы по ИНН | Вика |

## Куда добавить мой файл

| Что у вас есть | Куда класть |
|---|---|
| Код клиентской части | `frontend/` |
| Код основного сервера | `backend/` |
| Правила решения, расчёт, ИИ | `scoring-service/` |
| Имитация внешнего сервиса | `mocks/` |
| Демопрофили и тестовые данные | `data/` |
| Коллекция запросов | `postman/` |
| Схема, диаграмма, описание API, тест-сценарии | `docs/` |
| Новая переменная окружения | `.env.example` (и описать в разделе ниже) |
| Новая библиотека, образ или модель | `THIRD_PARTY_NOTICES.md` |

Пустые папки содержат файл `.gitkeep`: когда добавите первый настоящий файл, `.gitkeep` можно удалить.

## Правила работы

1. **Ветки.** В `main` не пушим. Работаем в ветке `feature/<имя>-<что>`, например `feature/liza-application-form`, и вливаем через pull request. В `main` попадает только то, что не ломает `docker compose up`.
2. **Коммиты.** Короткие и по делу: «Добавлена форма заявки», «Исправлен расчёт платежа». Не складывайте сутки работы в один коммит.
3. **Секреты.** Файл `.env` никогда не коммитим. Пароли и ключи только в `.env`, в репозитории только `.env.example` с фейковыми значениями.
4. **Имена.** Все файлы и папки пишем строчными буквами, латиницей, без пробелов. Windows и Mac не различают регистр, а Linux (Docker, VPS) различает, поэтому `Mocks` и `mocks` на сервере будут разными папками.
5. **Что не коммитим.** `node_modules/`, `target/`, `.venv/`, файлы IDE, веса моделей. Всё это уже в `.gitignore`.
6. **Зависимости.** Версии фиксируем (lock-файлы, точные версии в `requirements.txt`). Никаких `latest` в образах Docker.
7. **Перед слиянием** проверьте, что `docker compose up` поднимается.
8. **Если изменили контракт API** (поля, маршруты), сразу обновите `docs/api.md` и сообщите в чате команды.
