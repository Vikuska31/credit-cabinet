# Умный кредитный кабинет предпринимателя

Прототип цифрового кредитного конвейера для малого и микробизнеса (хакатон Альфа-Банка, кейс «Умный кредитный кабинет предпринимателя»). Клиент выбирает кредитный продукт, подаёт заявку и получает результат в личном кабинете, а банковская часть проверяет данные, считает оценку риска и принимает решение. Состояние заявки сохраняется и меняется последовательно.

> Этот README пока командный: он объясняет, что где лежит и куда добавлять свои файлы. К сдаче разделы внизу («Запуск», «Сценарий проверки» и другие) заполняются полностью, потому что по ним эксперты будут проверять проект.

## Правила работы

1. **Ветки.** В `main` не пушим. Работаем в ветке `feature/<имя>-<что>`, например `feature/liza-application-form`, и вливаем через pull request. В `main` попадает только то, что не ломает `docker compose up`. Пошаговая инструкция ниже, в разделе «Как работать с Git».
2. **Коммиты.** Короткие и по делу: «Добавлена форма заявки», «Исправлен расчёт платежа». Не складывайте сутки работы в один коммит.
3. **Секреты.** Файл `.env` никогда не коммитим. Пароли и ключи только в `.env`, в репозитории только `.env.example` с фейковыми значениями.
4. **Имена.** Все файлы и папки пишем строчными буквами, латиницей, без пробелов. Windows и Mac не различают регистр, а Linux (Docker, VPS) различает, поэтому `Mocks` и `mocks` на сервере будут разными папками.
5. **Что не коммитим.** `node_modules/`, `target/`, `.venv/`, файлы IDE, веса моделей. Всё это уже в `.gitignore`.
6. **Зависимости.** Версии фиксируем (lock-файлы, точные версии в `requirements.txt`). Никаких `latest` в образах Docker.
7. **Перед слиянием** проверьте, что `docker compose up` поднимается.
8. **Если изменили контракт API** (поля, маршруты), сразу обновите `docs/api.md` и сообщите в чате команды.

## Как работать с Git (пошагово)

Команды одинаковы на Windows (Git Bash) и на Mac (Терминал). Если удобнее VS Code, то ветки, коммиты и публикация доступны на вкладке Source Control, а pull request создаётся на сайте GitHub.

Единственный коммит прямо в `main` — самый первый, со структурой репозитория (его делает Вика). **Всё остальное идёт только через ветки и pull request.**

### Один раз: настройка
```bash
git config --global user.name "Ваше Имя"
git config --global user.email "почта-от-github@example.com"
```
Windows: установите [Git for Windows](https://git-scm.com) и работайте в **Git Bash**. Mac: введите `git` в Терминале, система предложит поставить нужные инструменты.

### Один раз: получить проект
Примите приглашение в репозиторий (письмо от GitHub), затем:
```bash
git clone https://github.com/<ник>/credit-cabinet.git
cd credit-cabinet
cp .env.example .env
```
При первом обращении откроется браузер для входа в GitHub.

### Каждый раз: цикл работы

**1. Обновить `main` и создать свою ветку**
```bash
git checkout main
git pull
git checkout -b feature/<имя>-<что>
```
Пример: `feature/liza-application-form`. Проверить, где вы: `git branch` (звёздочка у текущей ветки). Перед любой работой убедитесь, что вы **не** в `main`.

**2. Работать и коммитить**
```bash
git status
git add .
git commit -m "Короткое описание сделанного"
```
Перед `git add .` посмотрите `git status`: в списке не должно быть `.env`, `node_modules/` и других лишних файлов.

**3. Отправить ветку на GitHub**
```bash
git push -u origin feature/<имя>-<что>
```
В следующие разы достаточно `git push`.

**4. Создать pull request.** После пуша на странице репозитория появится плашка «Compare & pull request». Нажмите её, кратко напишите, что сделано, и нажмите «Create pull request».

**5. Влить в `main`.** Когда проверили, что `docker compose up` не сломался, нажмите «Merge pull request», затем «Confirm merge». Затем локально:
```bash
git checkout main
git pull
```

### Если ветка отстала от `main`
Другие уже влили свои изменения, а вы ещё работаете. Подтяните их в свою ветку:
```bash
git checkout main
git pull
git checkout feature/<имя>-<что>
git merge main
```
Если Git сообщил о конфликте, откройте помеченные файлы, оставьте нужный вариант, удалите маркеры `<<<<<<<`, `=======`, `>>>>>>>`, затем `git add .` и `git commit`. Если не уверены, как разрешить, спросите автора кода, который конфликтует с вашим.

### Если случайно закоммитили в `main` (но ещё не сделали push)
```bash
git branch feature/<имя>-<что>     # сохранить коммит в новой ветке
git reset --hard origin/main       # вернуть main к состоянию на GitHub
git checkout feature/<имя>-<что>   # перейти в новую ветку
```
`reset --hard` стирает также незакоммиченные изменения: если они нужны, сначала закоммитьте их.

### Если случайно закоммитили секрет (`.env`, пароль, ключ)
Сразу сообщите Вике, не пытайтесь «залить поверх». Секрет остаётся в истории, поэтому его нужно поменять, а историю почистить.

> Бесплатный GitHub не запрещает прямой пуш в `main` в приватных репозиториях, так что правило держится на договорённости. Смотрите на название ветки перед `git push`.
